# Profile Lookup API

A hosted API that accepts a profile URL and returns structured JSON —
built to the shape of a take-home brief that, read literally, asks for a
credential-based LinkedIn scraper. This is the honest version instead:
every skill the brief evaluates (architecture, API design, testing,
deployment, documentation, judgment) is demonstrated, without shipping
something that violates LinkedIn's Terms of Service or scrapes real
people's data without consent.

## Quickstart

Requires a JDK 17 or newer. The Maven Wrapper is committed, so a separate
Maven install isn't required:

```bash
git clone <this-repo>
cd profile-lookup-api
./mvnw spring-boot:run        # macOS/Linux
mvnw.cmd spring-boot:run      # Windows
```

No Maven installed and don't want to use the wrapper? Open the folder in
IntelliJ IDEA or VS Code with the Java extension — both auto-detect
`pom.xml` and can run `ProfileLookupApiApplication` directly.

**Windows note:** if `mvnw.cmd test` fails with something like
`UnsupportedClassVersionError ... class file version 61.0 ... up to 52.0`,
your `JAVA_HOME` is pointed at an old JDK (often a leftover Java 8 install)
even though a newer `java` is first on `PATH`. Point `JAVA_HOME` at a JDK
17+ install for this shell and re-run.

Once running (default port 8080), no credential is required to call it —
see "Public access & rate limiting" below:

```bash
# A profile that exists in the bundled fixture:
curl "http://localhost:8080/v1/profile?url=https://www.linkedin.com/in/example-profile"

# A well-formed URL with no fixture data -- the honest-failure path:
curl "http://localhost:8080/v1/profile?url=https://www.linkedin.com/in/anyone-else"
```

Interactive docs: `http://localhost:8080/docs` (Swagger UI, via
springdoc). OpenAPI document: `http://localhost:8080/v3/api-docs`.
Health check: `http://localhost:8080/actuator/health`.

Run the tests: `./mvnw test` (macOS/Linux) or `mvnw.cmd test` (Windows).

## API Documentation

This API is described using the [OpenAPI Specification](https://swagger.io/specification/)
(OAS — formerly known as Swagger) — the standard way to describe a
RESTful API's paths, parameters, and responses in a machine-readable,
tool-agnostic document. The document is generated by springdoc-openapi
directly from the controller code (`@Operation`/`@ApiResponses` on
[`ProfileController`](src/main/java/com/profilelookup/interfaces/rest/ProfileController.java)),
not hand-maintained, so it can't drift from what the endpoint actually
does — [`ProfileOpenApiTest`](src/test/java/com/profilelookup/interfaces/rest/ProfileOpenApiTest.java)
asserts the generated document actually lists every response code below.

- **Interactive docs (Swagger UI):** `http://localhost:8080/docs`
- **Raw OpenAPI document (OAS 3.1, JSON):** `http://localhost:8080/v3/api-docs`

`GET /v1/profile` accepts one query parameter, `url` (a LinkedIn profile
URL), and can return:

| Status | Meaning |
| --- | --- |
| 200 | Profile found; returns the available fields, omitting any not present |
| 400 | `url` is missing or not a syntactically valid LinkedIn profile URL |
| 404 | Live source is configured but no profile was available for this URL |
| 429 | Caller exceeded the per-address rate limit, or the source itself is rate-limited (`Retry-After` header) |
| 501 | No live data source is configured for this profile URL |
| 502 | The configured source returned a response it could not use |
| 503 | The configured source is unavailable or could not authenticate |

See "Source failures" below for what the 429/502/503 responses actually
mean and how they're modeled in code.

## Architecture

Clean Architecture / ports-and-adapters, sized to actually fit a project
this small — one port, not a sprawling hexagon:

```
domain/           Profile entity, ProfileSource port. Zero framework
                   imports -- compiles with plain javac, nothing else.
application/       ProfileLookupService (the use case). Depends only on
                   the ProfileSource interface.
infrastructure/    FixtureProfileSource and StubProfileSource -- the two
                   adapters actually shipped -- plus the config that
                   selects between them.
interfaces/rest/   Controllers, DTOs, filters, exception handling.
                   Depends on the use case; knows nothing about how
                   fixtures or the stub get their data.
```

Dependencies point inward only. `ProfileLookupService` has never heard of
`FixtureProfileSource`. `ProfileController` has never heard of either
adapter. The only file that knows both adapters exist is
`ProfileSourceConfig`.

## Live LinkedIn source

Default mode is still `fixture`.

```bash
export PROFILE_SOURCE=linkedin
export LINKEDIN_SESSION_COOKIE='your-cookie-header'
export LINKEDIN_PROFILE_URL_TEMPLATE='https://www.linkedin.com/in/{handle}'
./mvnw spring-boot:run
```

Do not commit cookies. Live misses return 404.

## Public access & rate limiting

The deployed challenge endpoint takes no API key or other credential —
an evaluator can call it directly. In its place, `/v1/**` requests are
rate-limited per caller address (token bucket, `RATELIMIT_CAPACITY` per
`RATELIMIT_REFILL_SECONDS`, both configurable). Exceeding the limit
returns HTTP 429 with a `Retry-After` header and a problem+json body.
This is a demo-scale, single-instance limiter: buckets live in memory,
so running more than one instance would need a shared backend (Bucket4j
supports a distributed/Redis mode, not implemented here).

## Source failures

Besides the "no live data source" 501 described above, the `ProfileSource`
port can report four classified failure kinds, each mapped to a stable,
documented problem+json response so a caller never sees provider-specific
detail (see `ProfileSourceException` and `GlobalExceptionHandler`):

| Failure | HTTP status | `type` suffix | `Retry-After` |
| --- | --- | --- | --- |
| Source can't authenticate with its provider | 503 | `source-unauthenticated` | — |
| Source temporarily unavailable | 503 | `source-unavailable` | — |
| Provider is rate-limiting the source | 429 | `source-rate-limited` | when known |
| Provider returned an unusable response | 502 | `source-upstream-error` | — |

No shipped adapter currently throws these (fixture and stub never fail
this way) — the classification exists so a future live adapter has a
safe, typed way to report *why* it failed, proven with a test-only
source implementation (`SourceFailureProblemResponseTest`).

## Decisions & trade-offs

**No Spring Security.** Neither the rate limiter nor (previously) API-key
auth needs a full security framework. Spring Security 7 (the version
shipping with Spring Boot 4) changed CSRF defaults in ways that
silently 403 REST APIs if misconfigured, and that's a hard thing to get
right without a live build to test against — which this project didn't
have (see "How this was built," below). A plain `OncePerRequestFilter`
is simpler, has less configuration surface, and does exactly the one
thing needed.

**Bucket4j core directly, not a Spring-integration starter.**
`bucket4j-core` has zero Spring dependency, so its compatibility with
whatever Spring Boot version you're on isn't a question. Buckets are
kept in a `ConcurrentHashMap`, one per caller address — correct for a
single instance, and documented as a scaling limit rather than solved
pre-emptively with Redis nobody asked for yet.

**RFC 9457 via Spring's native `ProblemDetail`**, not a hand-rolled error
DTO. Available since Spring Framework 6, so it costs nothing extra, and
every error response — validation failure, rate limit, unavailable
profile, classified source failure — uses the same shape with a stable
`type` URI a client can match on.

**Fixtures are derived from a real LinkedIn export's actual shape**
(Profile / Positions / Education / Skills / Certifications / Languages),
not an invented schema. The bundled sample is placeholder data — replace
`src/main/resources/fixtures/sample-profiles.json` with data from your
own export (Settings & Privacy → Data Privacy → "Get a copy of your
data") to demo against something real.

**OpenSpec from the first commit**, not retrofitted. The archived
`openspec/changes/archive/2026-08-28-add-profile-lookup/` change
contains the actual proposal → specs → design → tasks that were written
and validated (`openspec validate --strict`) before any code — the
Gherkin-style scenarios now living in `openspec/specs/profile-lookup/
spec.md` are exactly what `ProfileControllerIntegrationTest` tests
against, one scenario per test method, deliberately.

## How this was built, and what a real local build found

This project targets **Spring Boot 4.1.x** (current as of August 2026;
Boot moved to a new major version, 4.0, in November 2025 — if you're
used to 3.x, some defaults changed, notably Jackson 3 as the default
JSON library and stricter Spring Security 7 defaults, which is *why*
Spring Security was avoided here entirely).

The full wrapper build (`mvnw.cmd -B test`, `-B package`, and running the
packaged jar against a live health check and fixture lookup) has since
been run and verified green on a clean checkout with a JDK 17+ runtime;
the dependency coordinates in `pom.xml` (`bucket4j-core`,
`springdoc-openapi-starter-webmvc-ui`, the Spring Boot parent version)
resolved and worked as written. The one real issue a genuine local build
surfaced was environmental, not a `pom.xml` bug: on a Windows machine
where `JAVA_HOME` points at an old JDK (see the Windows note under
Quickstart), Maven forks the test JVM using that old JDK regardless of
what's first on `PATH`, producing a
`class file version 61.0 ... up to 52.0` error. The `maven-compiler-plugin`
`release` is still pinned explicitly to 17 rather than left to inherited
property translation, since this project's Java records make a
source/target fallback to 8 a silent breakage, not just a warning.

## Deploying

`render.yaml` targets Render's free tier (auto HTTPS, git-push deploy;
free-tier services spin down after 15 minutes idle, ~30–60s cold start
on the next request — fine for a demo, not for a real SLA). Any
container host works identically via the `Dockerfile`:

```bash
docker build -t profile-lookup-api .
docker run -p 8080:8080 profile-lookup-api
```

CI (`.github/workflows/ci.yml`) runs the wrapper test suite, packages the
jar, builds the container image, and validates every OpenSpec change with
`openspec validate --strict --all` on every push and pull request.

## Spec-driven development with OpenSpec

`openspec/specs/profile-lookup/spec.md` is the archived source of truth
for the core endpoint's SHALL/MUST requirements and WHEN/THEN scenarios —
the acceptance criteria `ProfileControllerIntegrationTest` is written
against, one scenario per test method, deliberately. It was promoted
there by `openspec archive add-profile-lookup` from
`openspec/changes/archive/2026-08-28-add-profile-lookup/`, which still
holds that change's original `proposal.md` and `design.md` (the
architectural decisions above, plus the rejected scraper approach, in
full) for historical context.

`openspec/changes/prepare-live-profile-source/` is the one still-active
change: the reproducible build, public (no-credential) access, classified
source failures, and complete OpenAPI contract described above, tracked
under its own `challenge-submission-readiness` capability rather than
folded into `profile-lookup`. Its own proposal/design/spec/tasks are all
current; the one item not yet checked off is the final manual step —
verifying the public HTTPS URL after deployment — which depends on
external resources (a GitHub repo, a Render service) this repository
doesn't create for you.

An earlier `add-oidc-self-lookup` change added a real "Sign In with
LinkedIn" OIDC adapter, correctly scoped to the authenticated caller's
own profile only. It was later removed (code, tests, and the OpenSpec
change alike) to keep the shipped surface to exactly `fixture` and
`stub` while the live-adapter decision remains pending — not because the
adapter was non-compliant, but to keep this repository's "what's
actually live" story to one sentence. `git log` has the full history if
you want to see it.
